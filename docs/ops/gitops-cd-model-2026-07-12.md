# GitOps / CD model (2026-07-12)

Codifies how code reaches production, wiring together the pieces added in the
CD/GitOps/IaC autopilot wave. Grounded in the existing branch contract (AGENTS.md)
and the manual deploy script (`scripts/deploy-prod-ecs.sh`).

> ## ⚠️ STATUS boundary
> The **pipeline artifacts** below are authored + verified to the extent possible
> without a cloud account. **Actual cloud provisioning + a live deploy is the E10
> gate** (`docs/adr/0003-hosting-aws.md`; `docs/deployment.md`: "actual cloud runtime:
> not yet provisioned"). Nothing here has been deployed to AWS.

## Branch contract (GitOps source of truth)
Per `AGENTS.md`:
- **`dev`** — integration / development desired state. All work merges here via PR + CI.
- **`main`** — **production desired state**. What is on `main` is what production should run.
- Promotion `dev → main` is a deliberate, reviewed merge; production deploys are driven
  from `main`, never from an ad-hoc branch.

## The pipeline
```
 commit ─▶ CI (ci.yml / web-ci / e2e / infra-ci / sca / golden)   ── every PR/push, blocking
        └▶ publish-images.yml  ── build + push server/web images → GHCR      [push main / dispatch]
                    │
   terraform (infra/terraform) ── IaC for the ECS runtime (ECR/cluster/services/ALB/…)
                    │              validated in CI; applied out-of-band once AWS exists
                    ▼
        deploy.yml ─▶ scripts/deploy-prod-ecs.sh ── roll ECS services   [dispatch + prod approval]
                    │  (OIDC AWS creds, `production` environment gate, migrate task, health smoke)
                    ▼
                  ECS Fargate: api + celery worker + celery beat (ap-northeast-2)
```

## GitOps model (declarative, git-as-source-of-truth)
- **Infrastructure** desired state lives in `infra/terraform` (reviewed via PR; `infra-ci`
  validates every change). Applying is currently manual (`terraform apply`) until an
  automated plan-on-PR / apply-on-merge-to-main pipeline is wired against a real backend.
- **Application** desired state = the image on `main` + the ECS service/task definitions
  in terraform. `deploy.yml` (approved) rolls the services to the `main` build.
- **Rollback** (per `docs/deployment.md`): re-deploy a previously verified image tag, or
  revert `main` and deploy — never an unrecorded console change.

## Golden visual-regression baselines (audit finding)
The `ui_kit` golden gate is currently a **no-op**: there are **zero baseline PNGs** and
every `goldenTest` is `skip: true` (`#31`). So `golden.yml`'s verify enforces no visual
regression today. Baselines are **generated on Linux CI**, not locally (local Windows
renders differ from CI; the guard hard-blocks local `--update-goldens`):
- A maintainer runs the **`golden.yml` generate job** via `workflow_dispatch` (the `#31`
  1-click approval). CI unskips the golden tests, runs `flutter test --update-goldens`,
  and auto-commits the baselines. After that the verify job enforces them.
This cannot be self-generated by an agent (the render must happen on CI). Documented in
`docs/ops/golden-baselines.md`.

## Remaining for real GitOps/CD (E10 gate)
- Provision AWS (VPC exists → run `infra/terraform`): the account decision is E10.
- Configure the GitHub `production` **Environment** (required reviewers) + OIDC deploy
  role secret + the `ASSEN_ECS_*` / `ASSEN_PROD_*` repo variables (terraform outputs).
- Set `vars.PROD_API_URL` to enable the web image publish.
- (Optional) automate `terraform plan` on PR + `apply` on merge-to-main once a state
  backend + a scoped CI role exist.
- Generate the golden baselines (maintainer dispatch).
