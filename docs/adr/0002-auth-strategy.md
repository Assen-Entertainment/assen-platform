# ADR-0002: 인증 전략 — opaque 토큰 + refresh 회전

- 날짜: 2026-06-12
- 상태: Accepted
- 결정자: 대표 (Geon Yong Kim) — 결정 스프린트 OQ-3, ralplan 합의(grand-design-plan 긴장점 3)

## 맥락

기존 아키텍처는 staged identity(anonymous_id→fan_id 병합)까지만 정의하고 최종 인증 방식을
Open Decision으로 남겼다. 모바일(iOS/Android) 앱과 웹을 동시에 지원해야 하고, 안전 기능
F11(차단 사용자 즉시 접근 제한)이 토큰 즉시 취소를 요구한다. 인증 코드는 인간 리뷰
게이트(#26) 대상이다.

## 결정

**opaque access token(서버 저장, 단명) + refresh token 회전**을 채택한다.

- access token: 서버(DB/Redis) 저장 opaque 값, 단명. 조회 시 서버 검증 — 즉시 취소 가능.
- refresh token: 회전(rotation) 방식 — 사용 시마다 재발급, 재사용 감지 시 토큰 패밀리 전체 무효화.
- 저장 위치(표면별):
  - **웹 = httpOnly 쿠키** (XSS 토큰 탈취 방어, CSRF 토큰 동반)
  - **모바일 = 플랫폼 보안 스토리지** (iOS Keychain / Android Keystore)
- 소셜 로그인 제공 시 **iOS 기준 Apple 호환 로그인을 함께 제공**한다(앱스토어 정책 —
  카카오 채택 시 애플 동시 제공).
- 휴대폰 본인확인은 가입 또는 첫 결제 시(#8). 사전등록은 경량 pre-open 캡처(OQ-4)라 비적용.
- PII(전화/이메일/이름)는 fan 프로필과 분리·암호화 저장, 최소 수집.

## 대안 검토

- **Django 세션 쿠키 단독**: 웹 적합하나 모바일 네이티브 앱에서 쿠키 세션은 표준 패턴이
  아니며 취약. 채택 안 함.
- **자체 발행 JWT(스테이트리스)**: 스테이트리스 이점이 P0 단일 모놀리스에선 무의미하고,
  토큰 취소·강제 로그아웃(F11)이 블랙리스트 없이는 구조적으로 어려움. 채택 안 함.

## 결과

- Ninja `auth=` 커스텀 인증 클래스로 구현한다. 토큰 발급/회전/취소 테스트가 Phase 4
  수용기준에 포함된다.
- Phase 3a의 mock 인증 스텁은 본 결정과 동일 인터페이스 계약을 따라야 하며, Phase 3b에서
  3a 통합 테스트를 수정 없이 실인증으로 재실행해 green이어야 한다(#31).
- 인증/세션/토큰 코드는 머지 전 인간 리뷰 필수(#26).
